Arquivos Novos
gastos/services.py Novo

Centraliza a comunicação com serviços externos. A função buscar_cotacoes() faz uma requisição HTTP GET para a AwesomeAPI e retorna um dicionário com a cotação do Dólar e do Euro em Reais. Se a API estiver fora do ar ou a conexão falhar, retorna None silenciosamente — o template exibe uma mensagem amigável em vez de quebrar a página. 

"""Serviços externos do app de gastos."""

import requests

AWESOMEAPI_URL = "https://economia.awesomeapi.com.br/json/last/USD-BRL,EUR-BRL"


def buscar_cotacoes():
    """Busca cotação atual do dólar e euro em reais via AwesomeAPI."""
    try:
        response = requests.get(AWESOMEAPI_URL, timeout=5)
        response.raise_for_status()
        data = response.json()
        return {
            "dolar": float(data["USDBRL"]["bid"]),
            "euro": float(data["EURBRL"]["bid"]),
        }
    except Exception:
        return None
  • URL da API: https://economia.awesomeapi.com.br/json/last/USD-BRL,EUR-BRL — retorna a última cotação do Dólar e Euro em JSON.
  • timeout=5: evita que a página trave caso a API demore mais de 5 segundos para responder.
  • raise_for_status(): lança exceção se a API retornar um código de erro HTTP (4xx/5xx).
  • except Exception → return None: garante que qualquer falha de rede não quebre a aplicação.
tests/test_integracao.py Novo

Contém os testes de integração que validam o fluxo de dados entre a aplicação e a API externa. Os testes usam unittest.mock.patch para simular a resposta da API sem depender de internet — isso garante que o CI (GitHub Actions) passe mesmo em ambientes sem acesso à web. 

"""Teste de integração: valida comunicação com a AwesomeAPI de cotações."""

from unittest.mock import Mock, patch

from gastos.services import buscar_cotacoes


def test_buscar_cotacoes_retorna_dolar_e_euro():
    """Verifica que a função processa corretamente a resposta da API."""
    mock_response = Mock()
    mock_response.raise_for_status.return_value = None
    mock_response.json.return_value = {
        "USDBRL": {"bid": "5.20"},
        "EURBRL": {"bid": "5.80"},
    }

    with patch("gastos.services.requests.get", return_value=mock_response):
        resultado = buscar_cotacoes()

    assert resultado is not None
    assert resultado["dolar"] == 5.20
    assert resultado["euro"] == 5.80


def test_buscar_cotacoes_retorna_none_em_falha():
    """Verifica que a função retorna None quando a API está indisponível."""
    with patch("gastos.services.requests.get", side_effect=Exception("Erro de rede")):
        resultado = buscar_cotacoes()

    assert resultado is None
  • Teste 1 — Sucesso: simula uma resposta válida da API e verifica se os valores de Dólar e Euro são extraídos corretamente.
  • Teste 2 — Falha: simula uma exceção de rede e verifica se a função retorna None sem lançar erro.
  • Por que mock? O CI roda em servidores do GitHub que podem não ter acesso à AwesomeAPI. O mock garante que os testes sempre passem independentemente da conectividade.
Procfile Novo

Arquivo lido pelo Railway (plataforma de deploy) para saber como iniciar a aplicação em produção. Em vez do servidor de desenvolvimento do Django (runserver), usamos o Gunicorn, um servidor WSGI robusto e adequado para produção. 

web: gunicorn config.wsgi --bind 0.0.0.0:$PORT
  • gunicorn config.wsgi: aponta para o arquivo WSGI em config/wsgi.py.
  • --bind 0.0.0.0:$PORT: a variável $PORT é definida automaticamente pelo Railway.
gastos/migrations/0001_initial.py Corrigido — estava ausente
⚠️ Este arquivo não existia na versão inicial do repositório clonado. A ausência causava o erro no such table: gastos_despesa ao tentar acessar a aplicação. Ele foi gerado com python manage.py makemigrations gastos e aplicado com python manage.py migrate.

O arquivo descreve a criação da tabela gastos_despesa no banco de dados SQLite com todos os seus campos: id, descricao, valor, categoria, data e criado_em.

  • Comando para gerar: python manage.py makemigrations gastos
  • Comando para aplicar: python manage.py migrate
  • Deve ser incluído no commit junto com os outros arquivos.

Abrir o Pull Request no GitHub (você faz)

  1. Acesse github.com/romes-dev/clone-Etapa-I
  2. O GitHub mostrará um banner "Compare & pull request" para a branch entrega-intermediaria — clique nele.
  3. Base: main ← Compare: entrega-intermediaria
  4. No corpo do PR, escreva: closes #1 (ou o número da sua Issue)
  5. Clique em Create pull request
  6. Aguarde o CI do GitHub Actions rodar e ficar verde ✅
  7. Clique em Merge pull request → Confirm merge
✅ Após o merge, a Issue será fechada automaticamente e o código estará na branch main.

Deploy no Railway (você faz)

  1. Acesse railway.app e faça login com sua conta do GitHub.
  2. Clique em New Project → Deploy from GitHub repo.
  3. Selecione o repositório clone-Etapa-I.
  4. Railway detecta automaticamente que é Python e usa o Procfile.
  5. Vá em Variables e adicione as seguintes variáveis de ambiente: 
    DJANGO_SECRET_KEY   = (gere uma chave longa e aleatória)
DJANGO_DEBUG        = false
DJANGO_ALLOWED_HOSTS = seu-app.up.railway.app
  6. Antes do primeiro deploy, Railway precisa rodar as migrações. Vá em Settings → Deploy e adicione o comando de build:
    python manage.py migrate
  7. Clique em Deploy e aguarde. Railway mostrará os logs em tempo real.
  8. Ao concluir, copie a URL pública (ex: https://clone-etapa-i.up.railway.app).
ℹ️ Para gerar uma DJANGO_SECRET_KEY segura, execute no terminal:
python -c "import secrets; print(secrets.token_hex(50))"
